# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Masmorra do Carrasco" — a souls-like action RPG in plain Three.js (browser, ES modules). No build step, no npm dependencies, no linter; the only tests are the online-world server's (`npm test`). Three.js and its addons (GLTFLoader, SkeletonUtils, BufferGeometryUtils, RoomEnvironment) are vendored in `vendor/`; `three` is resolved through the import map in `index.html`. All in-game text, UI, and code comments are in Brazilian Portuguese — keep new ones in Portuguese.

## Running

```bash
npm start            # node server.js → http://localhost:5173 (PORT env var overrides)
npm test             # node testes/mundo.test.mjs — o servidor de mundo (MMO), por HTTP, sem navegador
masmorra.exe         # (ou o atalho na área de trabalho) sobe o servidor e abre o jogo em janela de app
dotnet publish launcher -c Release -o .    # recompila o masmorra.exe (SDK .NET 8)
```

**O launcher (`launcher/`, gera `masmorra.exe`)** prende o servidor ao terminal: o log aparece nele, e fechar a janela ou Ctrl+C desliga o jogo — um Job Object (`KILL_ON_JOB_CLOSE`) garante isso até se o launcher for morto à força. Ele reconhece o jogo já no ar pela rota `/__saude` do `server.js` (`quem: 'masmorra-do-carrasco'`) e, com a 5173 ocupada por outro programa (é a porta do Vite), sobe na próxima livre via `PORT` — o `server.js` sozinho cairia com `EADDRINUSE`. O ícone é desenhado por `launcher/gerar-icone.ps1`. É uma cópia enxuta do launcher do editor de cenas.

`server.js` is a minimal static file server (plus the save, LAN-room and online-world routes). It exists because ES modules won't load over `file://`. There is nothing to compile, so edits show up after a browser reload. To check a change, load the page and play or inspect it. `window.game` exposes the `Game` instance in the console for debugging (e.g. `game.player.pos`, `game.inventory.add('greatsword', 1)`).

**O estático é uma lista BRANCA** (`FRENTE` em `server.js`: `index.html`, `css`, `js`, `vendor`, `assets`). Pasta nova que a página precise carregar tem de entrar nela; `saves/` e `mundo/` ficam de fora de propósito (o servidor escuta em todas as interfaces).

**ONDE O JOGO RODA (`js/hospedagem.js`, 02/10/2026)** — são três peças: as CONTAS no Supabase, o JOGO no GitHub Pages (`https://felisbertojpg.github.io/MMO-Project/`, repositório `FelisbertoJPG/MMO-Project`, a raiz da branch `main`) e o SERVIDOR DE MUNDO em outro lugar (ainda não há: ver `TASKS-MMO.md`). O Pages só entrega arquivos, então lá não existe `/__save`, `/__lan/*` nem `/__mundo/*`. Uma sonda em `/__saude` no carregamento decide: com o `server.js` por trás, tudo como sempre; sem ele (`temSaveEmArquivo()` falso), o save da Jornada vai para o `localStorage` (mais a nuvem, com conta), a sala só existe pela internet, e o Mundo online procura o servidor em `MUNDO_PADRAO` (vazio = "ainda não está no ar"). **Rota nova do `server.js` precisa de um plano para o Pages**, e **caminho novo de arquivo tem de bater maiúscula/minúscula** (o Pages diferencia; o Windows não). O `.gitignore` deixa de fora `saves/`, `mundo/`, os pacotes brutos e o `.exe`; publicar é `git push` (o Pages reconstrói sozinho).

**RECARREGAR PARA TODOS (`js/versao.js`, `assets/versao.json`)** — quem está com o jogo aberto segue no código antigo depois de um `git push`. Cada página lê `assets/versao.json` ao abrir e a cada minuto; quando o campo `versao` muda, ela avisa, grava o progresso, busca de novo os arquivos que carregou (`cache: 'reload'` — o Pages manda guardar tudo por 10 min, e sem isso a página recarregaria no código velho) e recarrega. **Quem decide é o push**: mudar `versao` recarrega todos em até um minuto; não mexer nela não incomoda ninguém. Mudança que altera o que VIAJA pela rede (o protocolo, o `MUNDO`) deve sempre subir com a `versao` nova — jogadores em versões diferentes no mesmo mundo é o que isto existe para evitar.

**O servidor de mundo no RENDER (`render.yaml`)** — plano grátis, que dorme sem visita e APAGA o disco a cada reinício. Por isso: `MUNDO_SAVES=nuvem` (o servidor não lê nem grava arquivo; o personagem mora em `masmorra.personagens`, migration 0002, lido e gravado pelo JOGO em `Mundo.lerDaNuvem`/`salvarNaNuvem`; o estado do mundo fica só na memória) e `FRENTE_EM` (o servidor não entrega o jogo: manda quem abrir o endereço para o Pages, para não gastar a franquia de tráfego). **Falhar em LER o personagem nunca vira "personagem novo"** — entraria zerado e gravaria por cima do de verdade. O `buildFilter` do `render.yaml` só reimplanta quando mudam os arquivos do servidor; `personagem_valido()` na migration é o `saveTorto()` em SQL — mudou um, mude o outro.

**`HOSPEDAR=1`** (servidor exposto para fora, atrás de túnel ou proxy): desliga `/__save` e `/__lan/*`. A defesa dessas rotas é "o pedido vem deste computador?" (`soDaqui`), e atrás de um túnel TODO pedido vem de `127.0.0.1`. Rota nova que confie em `soDaqui` precisa da mesma trava.

**Testar pela automação SEM estragar o save**: o jogo grava sozinho a cada 15 s e "Novo Jogo" APAGA `saves/progresso.json`. Antes de mexer: `game.salvar = () => {}` e `game.progresso = null; game.start()`. O `server.js` não manda cabeçalho de cache, e um Chrome de teste com perfil fixo pode rodar o `.js` VELHO depois de uma edição: desligue o cache (`Network.setCacheDisabled`). No mundo online, suba o servidor com `MUNDO_DIR` numa pasta temporária.

## Architecture

**`js/main.js` — `Game`** owns the renderer, scene, camera, and the single `loop()`. Every subsystem is constructed with `game` and reaches the others through it (`game.world`, `game.player`, `game.inventory`, `game.ui`, `game.sfx`, `game.effects`, `game.projectiles`, `game.all` = enemies + boss). Cross-system events are methods on `Game` (`onEnemyKilled`, `onPlayerDeath`, `rest`, `resetWorld`, `interact`, …). Game states are `loading` → `title` → `playing`. `game.menu` (`inventory`/`bonfire`/`pause`) freezes the simulation.
- Use `game.after(sec, fn)` for delayed game events rather than `setTimeout`. Its timers run in game time, so they respect menus, pause, and `hitstop`.
- Each frame: input → player/enemy updates → `separate()` (body pushing) → `world.resolve()` (wall collision) → projectiles/effects → camera.

**Asset pipeline (`js/assets.js`)**: All glTFs load up front. Characters come from two Quaternius UAL files (`UAL1`/`UAL2`), and their animation clips merge into `Assets.clips` by name. Dungeon props (KayKit) have to be listed in the `PROPS` array before `Assets.prop(name)` can use them; adding a new `.glb` without listing it breaks. Props get recolored in `tuneMaterials()`.

**Characters (`js/character.js`, `js/gear.js`)**: Every humanoid (player, skeletons, boss) is a `CharacterModel` cloned from the same UAL mannequin. Armor, bones, and weapons are procedural meshes built by `gear.js` **in the T-pose** and parented to skeleton bones, so they follow any animation. Animations are played by clip name (`model.play('Sword_Regular_A', …)`), and an unknown name only logs `Animação inexistente`. `initGear(renderer)` must run after assets load and before any model is built.
- **Os TRAJES vêm de ARQUIVO (30/09/2026)**: `buildOutfit(skel, kind)` veste o boneco com `assets/modelos/traje-<kind minúsculo>.json` quando `Assets.modelos` o tem (`vestirDoArquivo`: monta com `blocos.js` e prende cada peça no osso dela com `attach`, como o código fazia), e só cai no código (`buildOutfitDoCodigo`) sem o arquivo. Os arquivos saíram DESTE código pelo `importar-trajes.mjs` do editor, e um teste de lá garante que montam o mesmo boneco vértice a vértice. **Para mudar uma armadura, edite no Editor de modelo (botão "levar ao jogo")** — mudar o `gear.js` não muda nada enquanto o arquivo existir (reimporte com `importar-trajes.mjs ds --sobrescrever <tipo>`, que perde as edições do editor). Os ganchos `eyeMat` e `eyeAnchor` são garantidos mesmo que o traje editado os perca. Armas e escudos continuam no código.

**O GUERREIRO E O PROVADOR (`js/guerreiro.js`, `js/provador.js`, 03/10/2026)** — o CORPO DO JOGADOR, nos dois modos: o "Low Poly Axe Warrior" (loja da Unity), convertido por `ferramentas/guerreiro/converter.mjs` (three r185 próprio da pasta; conserta os ossos duplicados, a pose dos dedos, as peças de armadura giradas e o V das UVs) para `assets/guerreiro/guerreiro.glb` — o corpo nu em peças, três armaduras (`A1_`, `A2_`, `A3_` no nome da malha) e um esqueleto PRÓPRIO de 54 ossos. Faltando o `.glb`, todos ficam com o boneco antigo.
- **Retarget ao vivo**: o manequim UAL continua montado e animando (golpes, janelas de acerto, tudo igual), só que invisível; a cada quadro (`CharacterModel.update` → `CorpoGuerreiro.seguir`) cada osso do guerreiro recebe o giro que o osso UAL par (`PARES`) fez desde a pose T, e o quadril o deslocamento. A pose T do UAL vem do `Assets.baseScene` (nunca anima), por isso o corpo pode ser trocado no meio de um golpe. As armas vão para a mão do guerreiro (`pegada`) — e NÃO podem ser escondidas junto com o manequim (o bug da arma invisível).
- **O corpo** é `'antigo'` (o manequim) ou o CÓDIGO DA ARMADURA: um dígito por lugar (`LUGARES` do `ficha.js`: cabeça, peito, braços, pernas), 0 = nada, 1/2/3 = a peça do conjunto A1/A2/A3 do modelo — `'0000'` = nu (`NU`), `'2123'` = elmo e braços da malha, peito de couro, pernas de placas. Cada peça do `.glb` vai para um lugar pelo nome (`lugarDaPeca`: Helmet → cabeça, Forearm → braços, Boot/Pant/Knee/Thigh → pernas, o resto → peito). **A armadura vem do EQUIPAMENTO** (`Player.codigoDaArmadura`, aplicado em `refreshEquipment`); o provador (**Shift+G**) só escolhe entre o guerreiro e o boneco antigo (`corpoGuardado`: `'nu'` ou `'antigo'`). O corpo VIAJA no instantâneo (`c`, `protocolo.js`, conferido por `corpoValido`): o `JogadorRemoto` veste o mesmo (`vestir`); rastro antigo sem `c` = boneco antigo; os nomes de antes (`'A1'`…) ainda valem. Inimigos seguem com o manequim.
- **A malha fundida** (`vestir` → `geometriaFundida`): as peças do corpo escolhido viram UMA `SkinnedMesh` com UM `Skeleton` (os ossos de cada peça renumerados para a ordem da cena), no material com cor de vértice (as peças sem cor ganham branco). **Attacks**: The `ATTACKS` table in `character.js` maps attack keys to a clip, an optional `from`/`to` sub-range, a `hit` window (in clip seconds, measured from blade-tip velocity), and an `arc`. Player weapons (`items.js`) and enemy configs (`ENEMY_TYPES` in `enemies.js`, `BOSS_CFG` in `boss.js`) refer to attacks by these keys. If you retime a swing, update the hit window too.

**World (`js/world.js`)**: The dungeon is generated from the ASCII `MAP` (one char = one `CELL` = 6 m, from `S = 1.5` scale; north = −Z; `[row, col]` addressing). Doors, cell bars, and fog are defined as edges between two cells in `SPECIAL_EDGES`. Content is data tables of `[row, col]` cells: `TORCHES`, `CHESTS`, `PICKUPS`, `MESSAGES`, and enemy spawns in `spawnEnemies()` (`enemies.js`). The world keeps `interactables` (typed `pickup`/`torch`/`chest`/`door`/`fog`/`bonfire`/`message`/`bloodstain`), and `Game.interact()` dispatches on that type. Enemies pathfind on the same grid.

**A GUARDA E O ESCUDO NAS COSTAS (`Player.guarda`, 03/10/2026)** — com escudo, a guarda é o escudo (`Idle_Shield_Loop`); com arma de DUAS MÃOS (`twoHanded`), o escudo vai para as COSTAS (`CharacterModel.equipCostas`, preso ao `spine_03`/`Spine001`, `costasMatrix`) e a guarda é a própria arma (`Sword_Block` parado no quadro 0,45 s, estabilidade `guarda` do item — o espadão 0,5). - **AS DUAS MÃOS** (`CharacterModel.segurarComAsDuas`, ligado por `model.duasMaos`): os clipes do UAL são de uma mão, então, depois da animação (e do retarget), um IK de dois ossos (`ikDoisOssos`, giros no mundo) leva a mão esquerda ao cabo, `ABAIXO_NO_CABO` (11 cm) abaixo da direita, na MESMA pegada com que ela segura a tocha (`pegadaEsquerda`: dá o lugar do pulso e o giro da mão), com os dedos fechados na pose do `Idle_Torch_Loop` (`fecharDedosEsquerdos`, no manequim, antes do retarget); quando o cabo está longe demais para o braço esquerdo, o braço direito traz a arma para perto do corpo (a mão mantém o giro: a lâmina só anda). O cabo fica SEMPRE na frente do peito (`FRENTE_MIN`, nos eixos do tronco) e os cotovelos apontam para fora e para baixo (o `polo` do IK): sem isso o braço esquerdo atravessava o corpo até uma espada do lado direito. Fora em `MAO_OCUPADA` (comer, item, caído, descansando) e com a tocha; o peso entra e sai suave. O remoto liga pelo item que viaja (`d`/`e`) e pelo estado.
- **A EMPUNHADURA (`assets/empunhadura.json`, 04/10/2026) — a ESPADA SOLTA**: a espada não é presa à mão direita; ela tem lugar próprio e AS DUAS MÃOS VÃO ATÉ ELA (`segurarComAsDuas`). (1) a espada da animação (mão direita × pegada) anda inteira para a frente do peito (`frenteMin`), para o meio e até os dois pulsos alcançarem — com a pegada PADRÃO, para que mexer nas mãos não empurre a espada; (2) o AJUSTE vale como foi pedido: `espadaGiro` (gira em volta do ponto da mão direita) e `cabo` (anda: lado/alto/frente do tronco) — alcance a mão ou não; (3) cada mão corre no cabo por si: a direita em `armaPos`, a esquerda `maoEsq.abaixo` para o pomo; (4) PULSOS RETOS: cada mão escolhe o giro em volta do cabo E a posição do cotovelo (24 × 13 tentativas, com o cotovelo analítico `cotoveloDoIK`) que deixam a DOBRA do pulso mais parecida com a da animação, castigando cotovelo/antebraço dentro do tronco; depois do IK, `torcerAntebraco` gira o antebraço em volta do próprio eixo até a TORÇÃO do pulso ser a da animação (cotovelo e pulso não saem do lugar); por cima vem o giro pedido (`arma`, `maoEsq.giro`); com a mão presa, o braço se ajusta por `cotovelos` (o cotovelo gira em volta da reta ombro→pulso) e `bracos` (a torção do bíceps em volta do próprio eixo, devolvendo antebraço e mão ao lugar) — globais ou por chave nas camadas (`cotovelo_r/l`, `braco_r/l`, número no 1º campo, `extraDaCamada`); (5) a espada é posta onde foi calculada (`slotR.matrix = mão⁻¹ × espada`). `ik` mistura com a animação (0 = espada na mão direita, como no clipe). Medido nas 9 poses de teste: torção 0°, dobra quase sempre < 30°. Quem AJUSTA é a tela **Empunhadura** do editor de cenas (atalho "Empunhadura (editor)"; a cópia que vale é a de `Documents/projects/`): o jogador do jogo montado com os MÓDULOS DO JOGO (`/__alvo/ds/jogo/`); verde = a espada (W move, E gira), laranja/azul = as mãos (W corre no cabo, E gira o pulso); "salvar no jogo" grava o arquivo. `empunhadura(arma)` completa o que faltar com `EMPUNHADURA_PADRAO`; a arma se reconhece por `userData.arma`; a pegada de uma mão fica em `holder.userData.base`. **Mudar a conta do `segurarComAsDuas` muda o que a tela mostra** — ela não tem cópia. - **A pose e o grude (04/10/2026)**: `ik` é a FORÇA do grude no cabo (1 = IK como acima; 0 = mãos soltas, só a animação e as correções). `armaPos` é onde a mão direita segura na arma (a arma desliza na mão; os pontos das mãos não mudam). `camadas` são CORREÇÕES DE POSE por animação (`"<clipe>"` ou `"*"` para as sem camada própria): chaves `{ t, ossos: { "<osso do MANEQUIM>": [x,y,z] graus } }` em ordem de tempo; `corrigirPose` interpola e multiplica no osso do manequim ANTES do retarget (vale para o guerreiro e o boneco antigo) e antes do IK.
